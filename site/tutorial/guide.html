00 / Set up your workbench

Get it running locally

You’ll build Postcard Studio: an editor for a short message and a colour theme. Your text appears on a postcard as you type. Later, you’ll save it in the browser and add a keyboard shortcut.

How to follow each chapter

Read the explanation first. The short snippets show the ideas you’re learning; you don’t need to paste them into your app one by one.

When you reach Complete checkpoint, replace the listed files in src/postcard/ with the complete versions provided. You can copy or download each file, or use the chapter’s copy command. Then follow Try it to check the result in your browser.

Each checkpoint is a working version of the app. It’s fine to read through a chapter before changing any files.

This is a hands-on Glimlit guide, rather than an official Gleam tutorial. We’ll explain the language concepts we use as we go. Gleam is a small language that’s easy to pick up, so learning enough to get started doesn’t need a large investment of time. For a fuller introduction and reference, visit Gleam’s official documentation ↗ (opens in a new tab).

Install Gleam, and Node.js 20.19+ or 22.12+ with npm. Gleam is a programming language that compiles to JavaScript here. Vite runs the development server and rebuilds your app when files change.

  1. Clone the repository or download its ZIP using GitHub’s Code menu. Extract the ZIP if you download it.
  2. Open the project folder in your editor, and open a terminal in that folder. It contains package.json and gleam.toml.
  3. Run the commands below. Leave the development server running, and open http://127.0.0.1:3000/tutorial/. If port 3000 is already in use, stop the other server and run npm run dev again.

The repository includes the finished app. To build it gradually, work through chapter 01 and apply its checkpoint. The preview at the top of your local tutorial page runs the files you’re editing.

Keep npm run dev running. Use a second terminal in the same project folder for the checkpoint copy commands. Files left from later chapters are unused until you reach those chapters.

The files you’ll work in

The page, styles, and build setup are already connected. site/tutorial/index.html calls your app’s main(root) function. It provides a postcard-app element as the root for your templates. You don’t need to change the counter or todo app, or write a new build configuration.

Three ideas we’ll use

  • Model: the current state of the app, such as the postcard title.
  • View: a function that shows the model and turns user actions into messages.
  • Update: a function that takes the current model and a message, and returns the next model.

This is Model–View–Update, often shortened to MVU. Elm is a language and web framework that popularised this approach. You don’t need to know Elm to use it here.

Try it. Check that gleam --version and node --version work in your terminal. Then try the finished preview before replacing it with the first checkpoint.

01 / Model → View

Put state on screen

Start with a postcard that displays two strings. No editing, browser storage, or event listeners yet.

Give your state a shape

pub makes a definition available outside its module. type defines the shape of a value. The inner Model(...) is a constructor: calling it creates a model with named fields. Think of this record as an immutable JavaScript object whose fields have checked types. String is Gleam’s text type.

init() creates the starting model. fn defines a function, and its last expression is its return value. There’s no return keyword.

#(a, b) is a tuple: a fixed group of values. Our runtime expects a pair containing a model and a list of work to perform. [] is an empty list. For the first three chapters, leave that list empty. -> introduces the return type. You can read List(Effect(Msg)) as “a list of effects that can send messages.” We’ll use it in chapter 04.

The first checkpoint has a single placeholder message, NoOp. Its update function returns the model unchanged. We only need it to complete the runtime’s interface before we introduce real messages.

Render it with lit-html

Editor tip: make templates easier to read. Your editor may treat the markup inside a JavaScript tagged template literal as a string, without highlighting the HTML tags and attributes. In VS Code, install the lit-html extension ↗ (opens in a new tab) (bierner.lit-html) for template highlighting and HTML completions. Open Extensions, search for that identifier, and choose Install. It recognises templates tagged with html, including the ones below. This is an optional editor aid; the app works the same with or without it.

What does Model$Model$title mean?

Gleam generates this JavaScript function from the type above. Read its name as type $ constructor $ field: the first Model is the type, the second Model is its constructor, and title is the field to read.

Model$Model$title(model) reads the title, much like model.title does in Gleam. It does not change the model. Model$Model$message(model) reads the message instead. The dollar signs are ordinary characters in a JavaScript function name, not property access or special Glimlit syntax.

html is a JavaScript tag function applied to a template literal, the expression inside backticks. lit-html turns that template into DOM nodes. The view returns it; Glimlit puts it in the mount element. Expressions inside ${...} provide dynamic values. Text values render as text, so typing an HTML tag into a message will not execute it.

The compiler generates postcard.mjs from postcard.gleam. Import these functions from ./postcard.mjs using their exported names, as shown in the complete file. The build supplies that module; you do not create it or edit files in build/. Editor import completion can help you find the generated names.

Prefer shorter names?

JavaScript lets you give an imported function a local name with as. This is optional:

title is the same function as Model$Model$title, with the same types and behavior. If you choose an alias, use that name wherever you call the function in this file. Our checkpoints keep the generated names so you can see how they connect to Gleam; neither form changes how the app runs.

Connect the two languages

@external tells Gleam that the implementation of view lives in JavaScript. Its declaration states the types Gleam expects. dispatch is a function that accepts a message. The view returns View, an external type representing a lit-html template. The page passes its root element into main. The view also receives context: its id(name) helper creates IDs belonging to that app instance, so labels keep pointing to their own inputs when a page contains more than one postcard. Glimlit then commits that template to the mount. Nil means there is no useful return value, similar to JavaScript’s undefined. The function returned by main stops the app; the page already handles calling it when needed.

Try it. Change the title in init(), save the file, and find the new title on your local preview. You have changed the model and seen the view follow it. Browser controls and saving should not appear at this checkpoint.

02 / Complete the loop

Make the postcard editable

Add a title input and a message textarea. Their values drive the live preview, so send input messages to update the postcard model.

Not every keystroke needs a message. We keep these values in the model because the preview uses them immediately. A submit-only form could leave its draft in the inputs and read FormData when submitted. Focus, selection, and native controls can stay with the browser. Glimlit gives your app a loop; it does not require you to recreate browser behavior. See working with the browser.

A custom type can have several variants. Here, each message holds the text the user typed. case matches the variant and gives its data a name. The compiler checks that you handle every possible message. Model(..model, title: title) creates a new model by copying the existing fields and replacing the title. The previous model stays unchanged.

Send a message from the input

In JavaScript, Msg$UserChangedTitle("Hello") creates the same message as UserChangedTitle("Hello") in Gleam. Read the name as type $ constructor: the constructor belongs to Msg, and the argument is its text payload. It is an ordinary function call without new. Creating the value does nothing to the app until dispatch sends it.

@input attaches a DOM event listener. We prepare the named handler above the template so the markup stays easy to scan. The handler reads the input’s value, creates a Gleam message with its generated JavaScript constructor, and sends it with dispatch. The runtime calls update, stores the next model, and calls view again.

.value sets a JavaScript property on the DOM element, rather than its HTML attribute. live, imported from lit-html/directives/live.js, compares against the current DOM value. That helps keep user-edited controls in sync when the model changes, including when we add restore later.

lit-html updates the changing parts of the template. You don’t need to find the preview heading and set its text manually. The model is the shared source for both the editor and the preview.

Try it. Type into both fields. The preview should update immediately, and typing in the title must preserve the message. Refresh the page: your edits disappear because they only live in the model so far.

03 / More state, same loop

Give it a little colour

Add three colour themes. A theme is another custom type, but its variants carry no extra data.

The same naming rule gives us Theme$Coral(), Theme$Ocean(), and Theme$Meadow() in JavaScript. These constructors take no data, but JavaScript still needs () to call them. For example, Msg$UserSelectedTheme(Theme$Ocean()) creates the message for selecting Ocean. You can check a variant with a generated predicate such as Theme$isOcean(value), which returns a boolean.

Add theme: Theme to the model, initialise it with Coral, and add UserSelectedTheme(Theme) to the message type. Its update branch creates a new model with the selected theme. Using a custom type means Gleam won’t accept an arbitrary string where a theme is expected.

The view’s local themeName function uses generated theme predicates to pick the CSS class postcard-coral, postcard-ocean, or postcard-meadow. The theme buttons send messages just like the text inputs do. Their aria-pressed attributes communicate which choice is selected.

The styles are already in site/tutorial/styles.css. The editor uses regular CSS for readability; the project’s Tailwind setup is available if you prefer utility classes.

Try it. Switch colours, then change the text. Both should persist while you interact. Trace one button click through its message, update branch, model field, and CSS class. This is a complete interactive app with no effects or subscriptions.

04 / Work outside the model

Save with an effect

A model is an in-memory value. Writing to browser storage changes something outside that value. That work is an effect.

Keep update pure: for a given model and message, it returns the same next model and descriptions of work. It does not write to storage itself. Return an effect value instead of the empty list we have used so far.

Add a Notice type with Unsaved, Saving, Saved, and SaveFailed variants, and a notice: Notice field to the model. The view’s noticeText function chooses the feedback wording. Add messages for saving, success, and failure. Declare save_design as an external function implemented by saveDesign in effects.mjs.

The full file defines key and imports the message constructors. Calling saveDesign only constructs an object. Later, the runtime calls perform. It first renders the next model, so feedback like “Saving…” can be shown before work begins.

onSuccess creates a LocalStorageSavedDesign message; onFailure creates LocalStorageSaveFailed. Each goes through update to change the notice state. These constructors are imported with names such as Msg$LocalStorageSavedDesign and used directly without aliases or new. The same pattern applies to messages with and without data. Theme values use generated functions such as Theme$Ocean().

localStorage stores strings for this site in this browser. We use JSON.stringify to encode the design. It isn’t uploaded or shared across devices. Storage can be blocked, which is why the failure path matters.

Try it. Change the postcard and click Save design. Expect “Saved in this browser.” Refreshing still shows the defaults at this step: saving and restoring are separate operations. In your browser’s storage tools, look for the key glimlit.postcard.v1.

05 / Results become messages

Bring a saved design back

Add a Restore saved button. Reading storage is another effect. It returns either a saved JSON string or no saved value.

The update function returns [load_design()] when it receives UserClickedRestore. The effect’s result comes back as LocalStorageReturnedDesign(String) or LocalStorageWasEmpty. A failed read produces LocalStorageRestoreFailed.

Check data at the boundary

Saved strings are outside Gleam’s type system. They could have been edited or left by an older version. A decoder checks that the JSON has the fields and types we expect before we use it.

use is Gleam’s syntax for passing the rest of a block as a callback. Here it lets us read fields one after another, then combine their values. The decoder also matches the theme name to one of our three Theme variants.

json.parse(saved, decoder) returns a result: Ok contains a valid design; Error means decoding failed. The decoder is defined in the result message’s update branch, where its rules are used. Extend Notice with Restored, NoSavedDesign, InvalidSavedDesign, and RestoreFailed. A missing or invalid design changes the feedback message and preserves what you’re currently editing.

Restore is deliberate, rather than automatic at startup, so readers can see the full request → effect → result message → updated model flow.

Try it. Save a design, change the text and colour, then restore. Your saved version should return in both the preview and the form. Refresh and restore again. For the failure path, change the saved value to invalid JSON in your browser’s storage tools; restore should report the problem without losing your current draft.

06 / Ongoing sources of messages

Listen for a keyboard shortcut

An effect performs a piece of work. A subscription listens for messages over time. Our final feature lets the reader opt in to pressing N to cycle postcard colours.

Create subscriptions.mjs. Its nextThemeKey function describes a keyboard listener, but doesn’t attach it yet. The subscription has a start(emit) function that attaches the listener and returns a cleanup function.

The complete listener ignores input fields (including the shortcuts checkbox), textareas, select controls, editable content, held-down keys, events already handled by another listener, composition events, dialogs, and modifier shortcuts (including Shift). It prevents the default action only when it handles the shortcut. Typing an “n” into your postcard must keep working normally.

Start and stop through effects

Add shortcuts: Bool to the model. Bool has the values True and False. Toggling the checkbox returns [set_shortcuts(!model.shortcuts)]; ! flips the boolean.

The setShortcuts effect receives the app’s root and passes it to the keyboard source. Key events from that root bubble to its listener; shortcuts in another postcard stay independent. It uses the runtime’s subscription manager, which already knows where to send your app’s messages. It starts or stops a subscription under the key postcard-keys. Starting an already active key does nothing, and stopping a missing key is harmless.

The start/stop effect reports success with KeyboardShortcutsChanged(enabled). That message updates the checkbox’s model field. A setup failure produces KeyboardShortcutsFailed; update records ShortcutSetupFailed in the notice, and the view explains it. Each key press produces UserPressedNextTheme, which goes through the same update function as a button click. Update picks the next colour; the listener doesn’t reach into the DOM to change it.

Turning shortcuts off calls the cleanup function. Stopping the app also cleans up its subscriptions, and late messages from stopped listeners are ignored. That lifecycle is what distinguishes a managed subscription from an event listener left running indefinitely.

Try it. Enable shortcuts, then click the postcard preview to move focus away from the checkbox. Press N inside the postcard, outside an input field, to cycle colours. The order should be Coral → Ocean → Meadow → Coral. Type “nice” in the message: it should only enter text. Disable shortcuts, click the preview, and press N again: the colour should stay put.

Make it yours

You have the whole loop

You started with a model and a view, added messages to edit it, then used effects for browser storage and a subscription for keyboard input. Each feature feeds the same update function.

  • Add a signature field. Start with the model and messages, then update the view, save effect, and decoder.
  • Add a fourth theme. Let Gleam’s exhaustive case checks help you find the functions that need another branch.
  • Add a Reset button. Decide whether it changes only the draft or also clears the saved version; those are different operations.

Build and check your work

The tests include the finished tutorial’s state changes, storage behavior, and subscription cleanup. Run them with checkpoint 06 installed. Earlier checkpoints deliberately lack later features, so the finished-app tests won’t pass against them. The production build includes all site pages, including the demos, docs, and this tutorial.

If something goes wrong

  • Gleam reports a missing branch: you added a message or theme but haven’t handled it in a case. Use the error’s file and line number.
  • An import is missing: apply all files from the same checkpoint. The view and its Gleam messages need to match. Don’t edit files in build/; they’re generated.
  • The preview is blank: check the terminal and browser console. Keep the postcard-app mount element and the page entry script intact.
  • You want to start over: copy checkpoint 01 again. To return to the finished app, copy checkpoint 06. The full source remains in site/tutorial/checkpoints/.
