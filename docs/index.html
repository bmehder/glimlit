Getting started

Glimlit combines the Model–View–Update approach with lit-html’s JavaScript tagged template literals. Its primary use case is small interactive islands, such as forms, editors, filters, and widgets embedded in a larger page. The runtime provides the update loop, effect execution, subscription lifetimes, and cleanup. Applications choose their forms, dialogs, routing, and other browser behavior. The runtime lives in src/runtime/. The src/counter/, src/todos/, src/tutorial/, and src/recipes/ folders are example apps; src/site/ is the website. This repository includes the framework and browser examples; it is not currently a separately published package, and server-side rendering is not implemented.

Open http://127.0.0.1:3000/. The Demos page introduces Counter, Todos, and a recipe box that explores composition beyond the primary use case. Choose an example there, and the Postcard Studio tutorial walks through building an app from six complete checkpoints.

Starting an app

A model holds the state your application needs to reason about. Local interaction details can stay with browser elements. A message describes something that happened. Update takes the current model and a message and returns the next model plus any work to run. The view renders the model and dispatches messages from user events.

Import runtime/mvu and call mvu.start(init(), update, view). There is no separate subscription argument; apps start and stop subscriptions through effects.

mvu.start

initial
The result of calling init(): a pair of the initial model and a list of effects. Pass the result, not the function itself.
update
A function receiving the current model and a message, returning the next model and a list of effects.
view
A function receiving the model and a dispatch callback, returning Nil.
Return value
A function that stops the app and cleans up its subscriptions. Keep it for cleanup.

That page already provides #app. No module-specific Vite configuration is needed; the same page is included by npm run build.

What happens for each message?

  1. Update receives the latest model and the message.
  2. The runtime stores the returned model.
  3. The view renders it with a dispatch callback.
  4. The runtime schedules the returned effects; their result messages repeat the loop.

Startup begins with the result of init() and follows steps 2–4. Each call to mvu.start has its own model, runtime, and subscription manager.

Working with the browser

MVU gives application decisions a clear structure. It does not require every browser interaction to become a model field and message. lit-html views can work directly with elements, their properties, DOM events, and native controls.

Choose the owner of each value

Put it in the model when…Let the browser own it when…
The value affects shared data, a live preview, filtering, or coordinated behavior.A field’s unfinished value is only needed on submission.
The application needs to coordinate focus or restore a selection.Focus, the caret, or text selection can follow normal browser interaction.
A multi-step interaction needs application decisions or shared state.A native confirmation or a disclosure element already provides the local behavior.

State ownership is a choice. The postcard tutorial uses controlled inputs because edits drive a live preview. The recipe editor keeps a draft for validation and restoration. A submit-only field can stay in the DOM until its form is submitted.

A submit-only field

This template fragment leaves typing to the input, then sends a TitleSubmitted(String) message. Define and handle that message in your app. The model need not receive a message for every keystroke.

The browser’s required constraint applies before submission. Update or the data boundary should still validate the submitted value, including application rules such as rejecting whitespace-only titles.

Keep browser-owned fields mounted while editing. Decide explicitly when to reset a form or switch records. Writing a model value back to .value, especially through live, can overwrite an unsubmitted DOM value. Use the controlled binding shown earlier when the model is the intended source of truth.

Keep the runtime’s boundary small

Render functions describe the UI. Run local UI behavior in event handlers, rather than opening a dialog during rendering. Work requested by update uses effects; ongoing message sources use subscriptions with cleanup. Ordinary links and native form controls can continue to do their jobs.

Glimlit does not prescribe a router, form system, or dialog API. A larger app can choose its own libraries and conventions. See the project philosophy ↗ for the scope and the choices made by each example.

Effects

An effect is an object with deferred work and optional callbacks. Return effect objects from update; let the runtime execute them. Put these exports in src/app/effects.mjs; the declarations in Models & updates connect them to Gleam.

MemberContract
perform(context)Required. Returns a value or Promise. The context contains subscriptions and dispatch.
onSuccess(value)Optional. Converts the result into a message.
onFailure(error)Optional. Converts a thrown error or rejected Promise into a message.

The runtime supplies context when it calls perform; ordinary effects can ignore it. onSuccess and onFailure return messages, which the runner dispatches for you. Do not also dispatch the same result inside these callbacks.

Effects start in list order but are not awaited one after another. Completion order depends on the work. For dependent steps, have the first effect return a message, then request the second effect from that message’s update branch.

Without onSuccess, successful work sends no message. Without onFailure, a work failure rejects the runner’s Promise; it does not automatically update the model. mvu.start does not catch that rejection, so it can appear as an unhandled Promise rejection in the browser console. Exceptions from callbacks or dispatch are not reclassified as work failures. Supply a failure callback when the app needs to respond.

Subscription manager methods

MethodBehavior
start(key, source, dispatch)Calls source.start(emit) once for an inactive key. Returns no value.
stop(key)Disables emit and runs that source’s cleanup. Returns no value.
stopAll()Attempts cleanup for all active sources. Throws an AggregateError if any cleanup fails.
  • String keys are unique per app. Starting an active key does nothing.
  • Stopping an absent key does nothing. To change a source’s configuration, stop it and start it again.
  • Setup may emit immediately. Cleanup still runs if a message stops the subscription during setup.
  • Setup and cleanup must be synchronous. Setup must return a function, even if it is a no-op. If an effect has an onSuccess callback, it runs after setup returns; later source events arrive through emit.
  • Stopping disables emit before cleanup. App shutdown attempts all cleanups, even when one fails, then reports the collected errors.

Cleanup & lifecycle

Keep the function returned by your app’s entry point and call it when the app is no longer needed. For the illustrative src/app/app.gleam, your browser entry script can start it this way. The gleam: import identifies the module relative to src/, without the file extension or generated build path.

Stopping is idempotent: calling the returned function again does nothing. It does not remove the rendered DOM; remove or replace the mount content separately if needed. It cleans up subscriptions and ignores old view callbacks and pending effect results. It does not cancel work that is already running, such as an HTTP request. An effect that needs cancellation must arrange that separately.

Start the app once for each intended instance. Calling start repeatedly without calling the previous cleanup can leave multiple app lifetimes active.

Optional type checking

Gleam trusts each @external declaration. It does not inspect the JavaScript implementation to prove that the declared arguments and return value are correct. Glimlit does not change this FFI limitation.

You can still check the JavaScript side using the declarations Gleam generates and the runtime’s JSDoc types. This is an additional development check, separate from npm run build:

The command builds Gleam to refresh its .d.mts declarations, checks the files selected by jsconfig.json, and verifies type-checking examples under test/types/. What these checks do and do not cover

AreaCoverage
Generated model access and message argumentsChecked when JavaScript uses the generated declarations and typed parameters.
Effects and subscriptionsChecked against the runtime types you explicitly apply.
A Gleam external declaration matching its JavaScript exportNot automatically verified. A JavaScript annotation can disagree with the Gleam declaration and each side can still pass its own checker.
lit-html markup and event bindingsNot fully validated by these checks. Template expressions are JavaScript, but lit-html does not automatically give every event callback a precise DOM type. Annotate event handlers and narrow event.currentTarget before accessing element-specific properties.
Data from storage, networks, or other external sourcesNeeds runtime validation. Types do not validate JSON or prevent storage and network failures.
Disabled checking, any, and type assertionsCan bypass checks. Passing this command is not a guarantee of runtime correctness.

Keep checking optional

This repository’s jsconfig.json enables checking for source files named view.mjs, effects.mjs, and subscriptions.mjs, plus the runtime runner. Add other files to its include list as needed. Editors that use this configuration can show errors without running the command.

Use // @ts-nocheck on a file’s first line to opt out, as the tutorial app does. Its files need no JSDoc. To opt a file back in, remove that directive and add the relevant annotations; // @ts-check also makes the intent clear. TypeScript is another option for your JavaScript layer, but this repository’s existing app and external-file setup uses .mjs; a TypeScript implementation needs its own build configuration.

Troubleshooting

Start with the browser console for JavaScript errors and the development terminal for Gleam or build errors. Check the matching boundary before changing the runtime.

SymptomWhat to check
The app compiles, but nothing appears.Call the compiled main() from your browser entry point. Ensure #app exists before that call and your view calls lit-html’s render. See Views & dispatch.
An import or JavaScript export cannot be found.Check the relative @external path and exact export name. Use gleam:folder/module from a browser entry, or a relative generated .mjs import from source JavaScript. Keep handwritten JavaScript filenames distinct from generated Gleam filenames; no per-module aliases are needed. Run the build to regenerate Gleam modules; do not hand-edit build/.
An edit does not update the view.Dispatch a constructed message from the listener and handle it in update, returning the changed model. .value is lit-html property binding, not an attribute typo.
An effect never runs.Return the effect inside the list from init or update. Defining or constructing it is not enough. Keep the work inside perform, and check the app has not been stopped.
An effect finishes, but the model does not change.Supply onSuccess or onFailure to return a message and handle that message in update. Results from a stopped app are ignored.
Saving fails or the console reports an unhandled rejection.Handle expected work failures with onFailure. Browser storage can throw. Exceptions inside callbacks or update need their own fix; they do not go through the effect’s failure callback.
A subscription will not restart with new settings.An active key is ignored by start. Return stop and start effects in that order to replace the source. Ensure setup returns a cleanup function.
Listeners or timers fire twice.Check whether main() was called more than once without stopping the earlier app. Keep the returned cleanup and register it with your page lifecycle or Vite’s disposal hook.
