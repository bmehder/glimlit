Getting started

Glimlit combines the Model–View–Update approach with lit-html’s JavaScript tagged template literals. The runtime lives in src/runtime/. This repository includes the framework and browser examples; it is not currently a separately published package, and server-side rendering is not implemented.

Open http://127.0.0.1:3000/. The demo is at /demo/, and the Postcard Studio tutorial walks through building an app from six complete checkpoints.

New to Gleam or MVU? Start with the tutorial. This page explains the API and the behavior you can rely on.

Examples below use an illustrative app.gleam module and its generated app.mjs. Message types, models, storage keys, and browser effects belong to your app. The working counter, todos, and tutorial show complete modules and build connections.

Starting an app

Import runtime/mvu and pass the result of init(), your update function, and your view to mvu.start.

initial
A pair of the initial model and a list of effects.
update
A function receiving the current model and a message, returning the next model and a list of effects.
view
A function receiving the model and a dispatch callback, returning Nil.
Return value
A function that stops the app and cleans up its subscriptions.

The runtime stores each model before rendering it, then schedules its effects. Initialisation and later messages use the same ordering. Each app has its own model reference, runtime, and subscription manager.

Models & updates

Both init and update return #(Model, List(Effect(Msg))). The tuple separates state from requested work. An empty effects list means there is no work to perform.

The snippet assumes Model(title: String) and messages UserChangedTitle(String), TitleSaved, and TitleSaveFailed. save_title and log are typed external declarations for your JavaScript effect constructors. Constructing an effect does not perform it; update can stay pure.

Dispatch always reads the latest model, including when the callback came from an older render. Model values can stay immutable while the runtime privately keeps a reference to the latest value.

The html tag handles HTML-like markup and embedded JavaScript expressions. @input attaches a listener. .value sets the live DOM property rather than the initial HTML attribute; live compares against the current DOM value. Interpolated strings render as text. See Lit’s template expressions ↗.

JavaScript annotations are optional. The runtime’s JSDoc supports editor checking and the reference below; the tutorial files can stay plain JavaScript with // @ts-nocheck. The Gleam compiler checks the declared boundary, not the JavaScript implementation.

Effects

An effect is an object with deferred work and optional callbacks. Return effect objects from update; let the runtime execute them.

MemberContract
perform(context)Required. Returns a value or Promise. The context contains subscriptions and dispatch.
onSuccess(value)Optional. Converts the result into a message.
onFailure(error)Optional. Converts a thrown error or rejected Promise into a message.

Effects start in list order but are not awaited one after another. Completion order depends on the work. For dependent steps, have the first effect return a message, then request the second effect from that message’s update branch.

Without onSuccess, successful work sends no message. Without onFailure, a work failure rejects the runner’s Promise; it does not automatically update the model. Exceptions from callbacks or dispatch are not reclassified as work failures. Supply a failure callback when the app needs to respond.

Subscriptions

A subscription describes an ongoing message source. It exposes start(emit), which attaches the source and returns a synchronous cleanup function.

onTick creates a message; emit sends it to the app. The manager guards emit so a stopped subscription cannot dispatch late messages. Start and stop subscriptions using ordinary effects:

This example assumes ClockTicked(Int) is a message variant. Return these effect values through typed Gleam externals, just as you do for storage effects.

  • String keys are unique per app. Starting an active key does nothing.
  • Stopping an absent key does nothing. To change a source’s configuration, stop it and start it again.
  • Setup may emit immediately. Cleanup still runs if a message stops the subscription during setup.
  • Setup and cleanup must be synchronous. A start acknowledgement means setup returned.
  • Stopping disables emit before cleanup. App shutdown attempts all cleanups, even when one fails, then reports the collected errors.

Cleanup & lifecycle

Keep the function returned by your app’s entry point and call it when the app is no longer needed.

Stopping is idempotent. It cleans up subscriptions and ignores old view callbacks and pending effect results. It does not cancel work that is already running, such as an HTTP request. An effect that needs cancellation must arrange that separately.

Start the app once for each intended instance. Calling start repeatedly without calling the previous cleanup can leave multiple app lifetimes active.
